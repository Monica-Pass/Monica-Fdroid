# KDBX 密码删除与列表一致性验证

日期：2026-10-08；开发版本：1.0.318。

## 用户现象与范围

本体和系统分身关联同一本地外部 KDBX，未使用云同步。本体在“密码”页删除后原文件已进入回收站，列表仍逐步消失；分身在“密码库”页删除后列表先消失，原文件仍在原分组，随后条目重新出现。

使用新建合成数据库复现了客户端的问题，不需要假定用户文件已损坏。没有读取或修改用户的密码库。系统厂商分身没有在设备上复现；第二会话写入由测试 ContentProvider 在精确时序注入。

## 确认的原因

1. `VaultV2Pane` 全选后逐条调用 `deletePasswordEntry`。旧实现先更新 Room 为已删除，再异步逐条改写整个 KDBX，失败后回退 Room 状态。列表隐藏不代表原文件已完成。
2. “密码”页使用批量接口，但每 40 条保存一次完整 KDBX。300 条需要 8 次编码和文件保存。
3. 原生快照逐条写入 Room，反复触发列表更新。删除前已经读出的快照没有提交时的版本校验，可以在删除完成后重新显示已删除项目。
4. 外部文件完整写入后的校验失败，无条件回写旧恢复副本，能够覆盖另一会话刚完成的写入。

## 修改

- “密码”和“密码库”页共用密码批量删除命令，每个 KDBX 保存一次，确认原文件成功后批量更新列表。“密码库”页接入已有删除状态栏。
- 单条 KDBX 删除也先完成原文件操作，再修改列表；失败不隐藏项目。
- 选择项有失效 UUID 时，在写文件之前失败，不保存部分删除结果；去掉失败后逐条重试。
- 原生密码索引在后台通过 Room 事务发布，包含原有扩展字段更新；列表不再逐条加载或移除。
- 提交快照时与进程内原生写入共用数据库锁，核对当前原生版本；本地外部 URI 另核对文件哈希。拒绝过期快照，并在刷新流程中尝试重新读取一次。
- 外部文件完整写入后校验失败时保留当前文件及恢复副本，不用旧副本覆盖当前内容。文件写入中途的 I/O 失败保留已有恢复流程。

这仍是完整 KDBX 文件的原生保存，密码派生、加密、文件写入和校验需要时间；没有通过降低 Argon2 参数换取速度。

## 环境与测量

- 公共 AVD：`Monica_Issue136_API_32`，Android 32 / x86_64，测试用户 10。
- 300 条合成密码；KDBX 4.x；Argon2d，8 次，32 MiB，并行度 2。
- 使用真实 `KeePassKdbxService`、真实 `PasswordViewModel` 和独立内存 Room。外部 URI 由仅供 androidTest 的文件 Provider 提供。
- 在相同虚拟机上测量，耗时是调试构建的样本，不是所有手机的速度保证。

| 场景 | 修改前 | 修改后（普通版） |
| --- | --- | --- |
| 300 条密码批量删除 | 8 次保存，8,916 ms | 1 次保存，876 ms |
| 40 条“密码库”删除 | 列表 118 ms 隐藏，原文件约 25,819 ms 完成；40 次实际保存，另有 40 次读写权限探测 | 共用批量命令，1 次保存；含冷重读约 1,516 ms |
| 300 条初始索引 | 样本 1,144–5,185 ms，逐条发布 | 样本 113–262 ms，列表只出现 `[0, 300]` |

| 延迟提交旧快照 | 文件活跃 0，列表重新出现 300 | 文件和列表活跃均为 0 |

## 回归项目

`KeePassDeleteInvestigationTest` 共 8 项：

1. 300 条删除、原生回收站、失效缓存后的冷读取、列表整体提交、一次文件保存。
2. 40 条选中密码共享批量命令，一次文件保存。
3. 删除前快照延迟提交，不复活列表记录。
4. 单条写入被暂停时，列表仍保留该条目；释放后原文件和列表一致。
5. 写入权限故障，保留全部列表记录及原文件字节，不进行 300 次逐条重试。
6. 选择项含失效 UUID，不部分删除，不写文件。
7. 完整写入后注入另一会话的有效 KDBX，校验失败不覆盖它。
8. 冷加载仅发布完整列表。

`KeePassVaultDeleteUiTest`：实际渲染 `VaultV2Pane`，执行长按、全选、删除确认，断言 300 条全部进入原生回收站、页面条目消失、只保存一次。使用合成数据并恢复测试前筛选设置。

普通版：9 项设备测试通过；238 项 KeePass 单元测试通过。

F-Droid：9 项设备测试通过（数据层 8 项与界面 1 项分别运行在独立 instrumentation 进程）；238 项 KeePass 单元测试通过。300 条删除耗时样本 921 ms，1 次文件保存，列表数量为 `[300, 0]`。两版 Debug 应用和测试包均构建成功。

F-Droid 初次把两个测试类放在同一进程运行时，界面测试曾在删除操作之前报“没有 Compose 界面”及等待首个条目超时；没有应用崩溃。补充首帧等待后，仍需隔离数据测试和界面测试的进程状态。最终执行器逐类启动独立 instrumentation 进程，保留相同的真实页面操作和数据断言；不将早期失败运行计为通过。这是测试运行方式的限制，不宣称已修复一个未经确认的应用启动问题。

## 已有检查失败

扩大范围运行 `MultiPasswordSaveRegressionGuardTest`，两版均为 65 项中 6 项源码文本断言失败；从普通版 HEAD `97a9ce9e606d10c6d0aa112179639dfba6378c9f` 导出其引用源文件，以同一断言复核，也得到相同 6 项失败。未改写这些无关断言来掩盖失败：

- `addPasswordFromMdbxFolderPreservesFolderTargetAndShowsFolderPicker`
- `webDavBackupScreenManualCreateSharesCoordinatorQueue`
- `mdbxManagerLivesUnderDatabaseBackupAndUsesStandalonePages`
- `addPasswordAuthenticatorKeyFieldHasInlineScanAction`
- `inlineTotpPreviewMatchesSimplePasswordPreviewAndKeepsCountdownInSync`
- `webDavBackupsUseMonicaLocalContentScope`

因此不能宣称整个扩大测试套件全绿。本次相关 MDBX 批量提交保护断言仍通过。

## 边界

不同应用进程的文件写入无法仅靠进程内锁实现通用原子互斥。此次测试覆盖已确认的“完整写入后校验失败回滚覆盖”，不等同于验证任意厂商分身、任意文档 Provider 下的所有并发写入。实际用户文件是否另有问题仍未经文件检查确认。

未改变其他安全条目的独立删除实现，没有将全部 KeePass 页面改写为新架构。
