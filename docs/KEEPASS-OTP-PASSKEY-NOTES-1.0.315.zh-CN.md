# KeePass OTP、通行密钥与备注组合复核（1.0.315）

2026-09-29。复核用户报告：6 个 OTP 只有 2 个可见，缺少的 4 个与通行密钥共存；8 个通行密钥只有删除备注后才可见。

## 结论

- OTP 共存问题确实存在过：普通版提交 `49c6faba` 移除了 `entryToSecureItemData` 中遇到通行密钥就直接返回空值的判断，当前 main 已包含该修复。
- 当前通行密钥读取独立遍历所有原生条目，备注不作为排除条件；普通备注、受保护备注、多行备用码、长备注和空备注的组合均通过本次回归。
- 原生条目编辑器始终提供验证器入口。测试验证已有 OTP 的读取和修改，以及给原本仅含通行密钥的登录条目添加 OTP 后保存、关闭缓存重开。
- 本次没有修改运行代码。无法取得用户原始数据库，因此不将当前合成案例的通过结果等同于原始故障根因已被证明。

## 实际测试

复用公共 API 32 AVD，以真实加密 KDBX 3 / KDBX 4 文件调用正式 KeePass 服务，使用合成凭据和动态生成的 EC 私钥。

1. 8 条带通行密钥的登录记录，其中 4 条含 OTP，另有 2 条仅含 OTP：两次失效缓存重读均得到完整的 6 个 OTP 与 8 个通行密钥；同时核对 UUID、备注原文、私钥字节和底层文件字段。
2. 修改已有 OTP 的周期，并使用编辑器实际字段转换函数给另一条登录添加 OTP：保存后重读验证器，检查登录字段、备注和通行密钥字段不丢失。

两个测试均覆盖两种 KDBX 版本。普通版和 F-Droid 各 2 项设备测试通过，Debug / AndroidTest 构建通过；两个主目录及两份候选中的相关生产代码与新增测试一致。

测试不使用真实助记词或恢复码；临时数据库和本次合成私钥引用在结束时清理。公共 AVD 保持运行，原显示尺寸 840×2100 和字体缩放 1.5 未改动。
